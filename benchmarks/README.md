# Reproducible strategy comparisons

Build with JDK 17 and run with Python 3.10+ (standard library only):

```sh
./mvnw -Pbenchmarks verify
python benchmarks/run.py prepare
python benchmarks/run.py smoke
python benchmarks/run.py train
python benchmarks/run.py evaluate
python benchmarks/run.py scale
python benchmarks/run.py summary
```

On Windows use `mvnw.cmd` and set `JAVA_HOME` to JDK 17. The benchmark is an opt-in Maven module; normal `verify` does not run performance trials. `prepare` downloads four public RFC texts from RFC Editor; their URLs, lengths and SHA-256 digests are retained in the manifest. No public input or ephemeral credential is committed. The runner refuses to overwrite an existing input set or trial directory. Outputs are under ignored `benchmarks/results/`; payload files generated by each trial are deleted only after recording results, while result JSON and control evidence remain.

## Registered protocol

Five groups share real TLS 1.3 mTLS, HPKE, ZSTD, durable FileSink receipts and Finish output rereading:

| Group | Parameters |
| --- | --- |
| B0 | fixed 4 MiB / window 4 / ZSTD 3 |
| B1 | one globally selected fixed candidate, using training only |
| B2 | window only; chunk and compression bounds collapsed |
| WC | window + chunk size; compression bound collapsed |
| FULL | window + chunk size + compression level |

Six B1 candidates are declared in `run.py`. Each is repeated five times on training text/stable, mixed/step and mixed/slow-Sink trajectories, with candidate order rotated. Select the smallest geometric mean of per-group median completion-time ratios to B0. Freeze `selection.json` before evaluation. Evaluation uses distinct seeds and trace timings, never per-case parameter selection. Five independent JVM runs per strategy/case rotate strategy order. A JVM contains both peers and the proxy: CPU and memory therefore represent their combined footprint, not separate-host measurements.

Evaluation cases are stable text/mixed/entropy (512 MiB), bandwidth step with mixed data, high RTT with text, slow FileSink with mixed data, temporary disconnect with mixed data, three 1 MiB synthetic inputs, and a roughly 1 MiB concatenation of unmodified RFC 8446/9110/9111/9112 text. Training uses 128 MiB and a different seed. Mixed data alternates 64 KiB repeated text and pseudorandom bytes. Long-input size is explicit in `prepare --long-mib`; smaller runs are smoke evidence only. Check decision/trial counts before claiming steady-state evaluation.

The TLS-transparent proxy permits at most 16 connections, two bounded 32 × 16 KiB direction queues per connection, and 64 I/O workers. A shared per-direction byte scheduler bounds aggregate bandwidth. RTT is modeled by earliest packet departure time, with pipelined bounded queues; it is not a kernel network emulator. Stable traces do not add a bandwidth cap. Step traces use a shared per-direction token schedule with at most a 1 MiB burst and 64 → 8 → 64 MiB/s; training changes at 0.5/1.5 seconds, evaluation at 0.7/2.3 seconds. High-RTT added delay is 80 ms training / 120 ms evaluation (half in each direction). Slow Sink adds 80/160 ms inside each real commit after payload write, before force. Disconnect closes current proxy connections and refuses new ones for 300 ms at 0.7/1.0 seconds. Trace time starts when the proxy starts, including connection setup. These controlled scenarios retain real filesystem durability; they do not claim WAN or power-loss coverage.

The preselected improvement targets are step and slow Sink: at least 10% lower median completion time than B1, or at least 20% lower median application retry bytes with no more than 5% median completion regression (inapplicable when B1 retry bytes are zero). Stable/high-entropy regressions and all failures remain in the report. If FULL does not meet the targets, `python benchmarks/run.py confirm` performs one bounded simplification check: freeze compression at level 3 (WC), and rerun WC/B1 five times on step and Sink. This changes authenticated bounds, not policy-v1 thresholds. Do not continue tuning on the evaluation set.

## Measurements and boundaries

Completion includes Open/TLS establishment, sends, reconciliation, backoff, Finish and durable output verification. Independent full input/output SHA-256 validation follows, outside completion timing. CPU spans completion only. TLS upstream/downstream bytes count forwarded encrypted stream bytes including handshakes; TCP/IP headers and kernel TCP retransmissions are excluded. Application retry bytes count the full encrypted Chunk frames submitted for retry, including attempts that may not fully reach the socket; they are not packet-level retransmission bytes. ACK P95 and queue share use the shared last-64-valid-sample implementation, not a transfer-wide latency histogram.

RSS is sampled every 50 ms and includes the OS process high-water mark where available. Heap is the sum of per-pool peak usage (an upper bound, not necessarily simultaneous). NMT native committed memory is a snapshot at JVM exit, computed by subtracting Java heap from NMT total; it is neither peak native memory nor complete third-party allocation accounting. Missing metrics are null. Each peer reserves at most 512 MiB of application buffers and 8 MiB of receipt metadata; the effective initial window is recorded. JVM maximum heap is 2 GiB; the budget is not an RSS promise. Source preprocessing uses one compression worker. Controller counters and decision nanoseconds are constant-space.

`scale` checks a 4-chunk transfer against maxChunks 3 (must fail explicitly) and 4 (must complete), then compares short/long FULL transfers with the same preallocated 131072-slot metadata limits. It does not extrapolate arbitrarily large-file RSS from two samples. `summary` exports all raw JSON records and per-group median, P95, range, failures, retry bytes, trial/rollback counts and peak RSS. Public reports must omit personal paths, hosts and local execution diaries.

## Publishing a report

`python benchmarks/analyze.py` validates the complete registered matrix, computes throughput and uncertainty summaries, and writes the public report under `docs/experiments/feedback-v1`. It also reads `benchmarks/results/environment.json`: record the measured CPU, RAM, operating system, JVM, filesystem and storage there, using the fields in the published environment file. This environment input is separate from the anonymous per-run measurements. The report archives all training/evaluation/confirmation/resource records as deterministic gzip JSONL; exploratory smoke runs are excluded. No failed trial is silently rerun or dropped.

## Large index boundary checks

`python benchmarks/index_scale.py` runs separate 65,536- and 1,000,000-slot storage checks under a 256 MiB JVM heap limit after building the benchmark profile. It constructs a deterministic near-full journal fixture, then uses the real FileSink recovery/commit and source receipt reconciliation paths. It verifies exact metadata budgets, last-slot idempotence, explicit overflow refusal, full-index reopening and payload bytes. It is not a million-request network benchmark. Results and scope are in the [index report](../docs/experiments/index-scale-v1/README.md). Generated fixtures remain under ignored results; a new `--output` directory is required for another run.

`FrameAllocationRun` 是独立帧转换分配诊断，不运行吞吐矩阵；方法、参数、每端分配/峰值工作集与窗口见[诊断报告](../docs/experiments/frame-allocation-v1/README.md)。

`BenchmarkRun` 另支持 `journal` 诊断场景，在持有 receipt 日志锁时注入与 `sink` 相同的提交延迟；不自动加入原五策略评测矩阵。输出新增 persistShare、effectiveFinalWindow 和各维试探完成计数，见[诊断报告](../docs/experiments/feedback-diagnostics-v1/README.md)。

## Frozen pipeline reevaluation

[Pipeline protocol](../docs/pipeline-protocol.md) retains policy v1. Use `run.py --output benchmarks/results/pipeline-v1 --processors 4` with each phase to keep a separate evidence set and a fixed JVM processor count. The remaining heap, buffer, data and repetition settings retain the registered protocol. `analyze.py --output benchmarks/results/pipeline-v1 --report docs/experiments/pipeline-v1` refuses to overwrite an existing published report. Verify the input manifest before reuse; evaluation starts only after the new training selection is frozen. Cross-report timings are not a controlled pipeline A/B comparison.

## Complete control-cycle diagnostics

`python benchmarks/control_diagnostics.py NEW_OUTPUT` runs a separate fixed 30-case diagnostic after `mvnw -Pbenchmarks package -DskipTests`. It records fresh JVMs, input/source hashes, all outcomes, and a gate requiring completed two-round evaluations in every dimension of every long transfer. The optional `BenchmarkRun ... control-cycles` profile applies only to FULL or V2, caps its chunk range at 1 MiB, and leaves policy v1 thresholds and the frozen performance matrix unchanged. See the [method and results](../docs/experiments/control-diagnostics-v1/README.md). Keep other host workloads idle for reproduction; diagnostic timings are not performance acceptance.

## Policy v2 comparison

After building with `mvnw -Pbenchmarks package -DskipTests`, run `python benchmarks/policy_v2.py NEW_OUTPUT`. The comparison matrix contains 18 fresh JVMs: FULL-v1, V2 and FIXED × sink/journal × three repetitions, with rotated strategy order, identical 512 MiB input and resource limits. FIXED here is 1 MiB/window 4/level 3, not the previously trained B1. Both dynamic groups use the diagnostic 1 MiB chunk ceiling. The script retains all outcomes, stops on correctness/process failure, and requires completed window/chunk evaluations. `--summarize` recomputes descriptive paired comparisons from an existing directory without rerunning transfers. Do not run builds or other load tests concurrently with the measurement.

## Changing receiver capacity: window-only research study

The [frozen protocol](../docs/window-study-protocol.md) asks whether existing window feedback reduces initial-configuration sensitivity while staying within 10% of the best measured fixed window. It compares F1/F2/F4 with v2 A1/A4 in 15 fresh JVMs; all groups use identical chunks, compression, input and a 4 → 1 → 4 admission-capacity trace. This is an isolated window experiment, not a new policy or a rerun of the B1 matrix.

Set `JAVA_HOME` to JDK 17 and use Python 3.10+:

```sh
./mvnw -Pbenchmarks verify
python -m unittest discover -s benchmarks -p test_window_adaptation_report.py -v
python benchmarks/window_adaptation.py benchmarks/results/window-study-new
python -m pip install -r benchmarks/requirements-plots.txt
python benchmarks/window_adaptation_report.py benchmarks/results/window-study-new docs/experiments/window-study-new
```

Use `mvnw.cmd` on Windows. Install plotting dependencies before measurement or after the matrix completes. Both output directories must be new. Allow roughly 5 GiB for the shared input and retained receiver outputs. Each process has a 300-second limit; any failure is retained and stops the matrix without an implicit retry. Keep builds and other load tests separate from measurement. The runner needs no external dataset or service.

The report command performs no transfers: it validates completeness/integrity, summarizes all repeats, archives the 250 ms traces and renders one four-panel PNG/SVG using preselected repetition 0. Matplotlib is required only for plotting; the runner and analysis tests use the standard library. Response times require a sustained two-second window band and exclude the verification tail. Raw records, method, result interpretation and limitations are in the [published window study](../docs/experiments/window-adaptation-v1/README.md).
