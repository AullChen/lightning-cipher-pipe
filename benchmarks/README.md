# Reproducible strategy comparisons

Build with JDK 17 and run with Python 3.10+ (standard library only):

```sh
./mvnw -Pbenchmarks verify
python benchmarks/run.py prepare
python benchmarks/run.py smoke
python benchmarks/run.py train
python benchmarks/run.py evaluate
python benchmarks/run.py scale
python benchmarks/run.py summary
```

On Windows use `mvnw.cmd` and set `JAVA_HOME` to JDK 17. The benchmark is an opt-in Maven module; normal `verify` does not run performance trials. `prepare` downloads four public RFC texts from RFC Editor; their URLs, lengths and SHA-256 digests are retained in the manifest. No public input or ephemeral credential is committed. The runner refuses to overwrite an existing input set or trial directory. Outputs are under ignored `benchmarks/results/`; payload files generated by each trial are deleted only after recording results, while result JSON and control evidence remain.

## Registered protocol

Five groups share real TLS 1.3 mTLS, HPKE, ZSTD, durable FileSink receipts and Finish output rereading:

| Group | Parameters |
| --- | --- |
| B0 | fixed 4 MiB / window 4 / ZSTD 3 |
| B1 | one globally selected fixed candidate, using training only |
| B2 | window only; chunk and compression bounds collapsed |
| WC | window + chunk size; compression bound collapsed |
| FULL | window + chunk size + compression level |

Six B1 candidates are declared in `run.py`. Each is repeated five times on training text/stable, mixed/step and mixed/slow-Sink trajectories, with candidate order rotated. Select the smallest geometric mean of per-group median completion-time ratios to B0. Freeze `selection.json` before evaluation. Evaluation uses distinct seeds and trace timings, never per-case parameter selection. Five independent JVM runs per strategy/case rotate strategy order. A JVM contains both peers and the proxy: CPU and memory therefore represent their combined footprint, not separate-host measurements.

Evaluation cases are stable text/mixed/entropy (512 MiB), bandwidth step with mixed data, high RTT with text, slow FileSink with mixed data, temporary disconnect with mixed data, three 1 MiB synthetic inputs, and a roughly 1 MiB concatenation of unmodified RFC 8446/9110/9111/9112 text. Training uses 128 MiB and a different seed. Mixed data alternates 64 KiB repeated text and pseudorandom bytes. Long-input size is explicit in `prepare --long-mib`; smaller runs are smoke evidence only. Check decision/trial counts before claiming steady-state evaluation.

The TLS-transparent proxy permits at most 16 connections, two bounded 32 × 16 KiB direction queues per connection, and 64 I/O workers. A shared per-direction byte scheduler bounds aggregate bandwidth. RTT is modeled by earliest packet departure time, with pipelined bounded queues; it is not a kernel network emulator. Stable traces do not add a bandwidth cap. Step traces use a shared per-direction token schedule with at most a 1 MiB burst and 64 → 8 → 64 MiB/s; training changes at 0.5/1.5 seconds, evaluation at 0.7/2.3 seconds. High-RTT added delay is 80 ms training / 120 ms evaluation (half in each direction). Slow Sink adds 80/160 ms inside each real commit after payload write, before force. Disconnect closes current proxy connections and refuses new ones for 300 ms at 0.7/1.0 seconds. Trace time starts when the proxy starts, including connection setup. These controlled scenarios retain real filesystem durability; they do not claim WAN or power-loss coverage.

The preselected improvement targets are step and slow Sink: at least 10% lower median completion time than B1, or at least 20% lower median application retry bytes with no more than 5% median completion regression (inapplicable when B1 retry bytes are zero). Stable/high-entropy regressions and all failures remain in the report. If FULL does not meet the targets, `python benchmarks/run.py confirm` performs one bounded simplification check: freeze compression at level 3 (WC), and rerun WC/B1 five times on step and Sink. This changes authenticated bounds, not policy-v1 thresholds. Do not continue tuning on the evaluation set.

## Measurements and boundaries

Completion includes Open/TLS establishment, sends, reconciliation, backoff, Finish and durable output verification. Independent full input/output SHA-256 validation follows, outside completion timing. CPU spans completion only. TLS upstream/downstream bytes count forwarded encrypted stream bytes including handshakes; TCP/IP headers and kernel TCP retransmissions are excluded. Application retry bytes count reissued encrypted Chunk frames, separately. ACK P95 and queue share use the shared last-64-valid-sample implementation, not a transfer-wide latency histogram.

RSS is sampled every 50 ms and includes the OS process high-water mark where available. Heap is the sum of per-pool peak usage (an upper bound, not necessarily simultaneous). NMT native committed memory is a snapshot at JVM exit, computed by subtracting Java heap from NMT total; it is neither peak native memory nor complete third-party allocation accounting. Missing metrics are null. Each peer reserves at most 512 MiB of application buffers and 8 MiB of receipt metadata; the effective initial window is recorded. JVM maximum heap is 2 GiB; the budget is not an RSS promise. Source preprocessing uses one compression worker. Controller counters and decision nanoseconds are constant-space.

`scale` checks a 4-chunk transfer against maxChunks 3 (must fail explicitly) and 4 (must complete), then compares short/long FULL transfers with the same preallocated 131072-slot metadata limits. It does not extrapolate arbitrarily large-file RSS from two samples. `summary` exports all raw JSON records and per-group median, P95, range, failures, retry bytes, trial/rollback counts and peak RSS. Public reports must omit personal paths, hosts and local execution diaries.
